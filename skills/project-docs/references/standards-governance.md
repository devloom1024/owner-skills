# 规范形成与采纳

用于从项目实践提炼规范、维护已有规范，以及判断缺陷经验是否值得成为长期规则。采用项目现有命名、决策流程和存放位置；本文描述判断依据，不要求增加状态字段、审批文件或固定目录。

## 分开记录采纳与验证

| 维度 | 判断依据 | 不能据此推断 |
|---|---|---|
| 项目是否采纳 | 有效 AGENTS、正式规范、维护者决定或项目认可的决策记录，明确适用范围。无此证据时仅作为候选；旧文档状态不清时标未确认。 | 重复实现、测试存在或某次 CI 通过，不等于项目已采纳此规则。 |
| 如何验证和约束 | 具体脚本、测试或人工审查方法，覆盖的失败模式、启用范围及本次实际结果。 | 规则已采纳不等于已自动强制；检查通过不等于覆盖整条规则。 |

- `observed` 仅表示从实现或实践观察到的现象，不是采纳状态。
- `adopted` 需要可追溯的项目采纳依据；已有有效规则无需重新审批，修订仍遵循项目流程。
- `test-backed`、`mechanical`、`review-only` 描述验证依据或方式，可以组合；缺少证据时说明 `unknown` 或项目等价状态。仅写下测试命令不能证明测试已运行。
- `enforced` 仅用于已确认在所述范围启用、会阻止违规通过的门禁；标明覆盖范围和剩余人工检查。存在脚本、可选 CI 或一次成功结果不足以支持这一声明。

不把这些词排成单一生命周期。例：仓库已有资源清理测试，但没有要求所有包采用同一模式时，只能得到有测试依据的规范候选；项目正式要求的设计审查规则可以是 `adopted` 且 `review-only`。沿用项目旧状态名时补足对应证据，不为统一术语批量迁移。

## 从实践形成规范

1. **定位来源**：检查脚本、CI 配置、测试、生成器、现有规则及重复实践。分清“工具目前这样执行”“实现通常如此”和“项目要求如此”；确认命令作用、调用关系、适用范围与例外。
2. **筛选可复用规则**：提炼稳定的不变量、适用边界、失败模式和理由。局部实现细节留在源码或 subsystem；一次临时绕过不升级为跨项目规则。
3. **对照既有规范**：优先补充或链接已有 owner。发现实现、检查和已采纳规则冲突时，分别报告偏差，不以实现数量或检查通过来改写项目要求。
4. **提出可审阅候选**：写清建议规则、来源、置信度、范围、例外、验证方式和待决定事项。普通文档编辑授权不等于授权采纳新的工程政策；没有采纳依据时保持候选，不写入 AGENTS 的强制指令。
5. **按项目决定落地**：已有采纳记录或明确授权采纳该规则时，直接完成授权范围内的文档修改，不重复要求确认。记录采纳依据，更新 owner 与导航；新增 CI、修改实现或启用阻断门禁仍需要对应任务范围。

已有门禁可以如实记为技术约束，但不能由此推导项目已决定扩大其适用范围。未经验证的来源或过时规则保留证据缺口，不为了完整性发明正式状态。

## 规范的最小内容

按项目模板组织，至少让读者找到以下信息；可链接已有 owner，不重复复制事实：

- 适用范围、排除范围及规则本身；说明哪些要求已采纳、哪些仍是建议。
- 规则理由、具体失败模式和证据来源；必要时链接事故、审查发现或设计决定。
- 验证方式：脚本或测试位置、人工审查判据、覆盖范围及盲区；运行记录与规则正文分开，避免把一次通过写成长期保证。
- 合理例外、采纳或修订依据，以及按项目流程需要的例外决定；不虚构维护者、审批人或检查结果。

## 从缺陷经验提出提升

先保留缺陷事实：现象、影响、根因、修复、如何更早发现以及证据。优先使用项目已有 postmortem、incident 或 Lessons 层；局部缺陷可留在 PR 和回归测试中，不为每次修复另建永久文档。

提出提升为规范时检查：

1. **规则稳定**：能解释因果并预防一类失败，而非把本次补丁或临时 workaround 固化为通用要求。
2. **范围明确**：能说清适用组件、触发条件、反例和例外，并判断是否已有规则覆盖。
3. **有检测办法**：指出能检测对应失败模式的测试或门禁，附实现或结果证据。缺失时列为待补验证；确实不能自动化的规则需给出可操作的人工判据和局限，由项目明确接受 `review-only`，不宣称已自动防复发。
4. **有项目决定**：满足技术条件只支持提出候选；正式采纳依项目流程或明确授权。项目要求多次独立事故或重复审查记录时检查该阈值，但不自设统一次数。

暂不具备条件时保留经验与改进建议，不强行升格。采纳后由规范拥有通用规则，事故记录继续拥有历史因果与证据，二者互相链接，不把历史记录重写成当前规范。
