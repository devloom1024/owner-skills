# 文档初始化

用于新项目或已有代码但缺少文档基线的项目。单页修订和已有体系的局部整理不重跑初始化。先沿用项目现有入口、命名和规则；“最小交付”是所需信息，不是固定文件配额。

## 从证据形成初稿

1. 确定仓库、目标读者和授权范围，识别已有文档与有效 `AGENTS.md`，不覆盖用户修改。
2. 查看主要入口、manifest、源码边界、配置、脚本、测试、CI、生成器和当前决策。先识别实际运行路径，再提出 subsystem 边界；不把每个源码目录都变成文档目录。
3. 依据 [文档模型](document-model.md) 选择最小入口及事实所有者。小项目可以先在 README 中组织必要章节；跨文件主题、包契约或机器契约确有独立维护需要时再拆分。
4. 从证据生成可用的初始内容，而不只给空目录和标题。每项关键事实附来源；不能确认的产品语义留在未决项，不要求维护者从零编写全部内容。
5. 从脚本、CI、测试、生成器和重复实践识别规范候选，按 [规范形成与采纳](standards-governance.md) 区分既有规则与待决定的建议。没有候选时说明即可，不为填满结构发明规则。
6. 建立主要代码路径、事实源、文档 owner 和验证入口的初始映射；已有声明可复用，推断须带证据与置信度。缺少明确 owner 时给出候选和理由，不擅自指定维护者。
7. 规划或审计只输出方案；用户要求初始化时直接创建授权范围内的文档，修复导航并运行适用检查。未决规范不阻塞已知事实的落地，也不因初始化而改写实现或新增 CI 门禁。

## 最小交付信息

| 交付项 | 应能回答的问题 |
|---|---|
| 最小文档布局和入口 | 从哪里开始读，各页面或章节由谁拥有，为什么需要独立文件？只列有内容的路径，不创建占位目录。 |
| 有证据的初始内容 | 项目现在做什么，主要运行路径、边界和验证入口是什么？没有实现时只写已有事实，目标另标为计划。 |
| subsystem 和规范候选 | 哪些主题值得独立维护，哪些实践可能成为规则？附来源、置信度、采纳依据或待决定项。 |
| 初始所有权映射 | 主要代码或契约变化应更新哪里，事实源和检查是什么？复用项目现有索引或表格，不强制新建 YAML。 |
| 未决语义与验证缺口 | 哪些产品行为、边界或规范尚不能确定，需要什么证据或项目决定？哪些命令没有运行？ |

这些信息可以分布在实际文档和交付说明中，不要求额外创建一份永久治理报告。规划阶段提供候选布局与内容草案；编辑阶段以实际文件及验证结果交付。

映射可使用以下字段，并按项目已有格式调整：

| 代码路径或契约 | 事实源 | 文档 owner | 映射依据 | 验证入口 |
|---|---|---|---|---|
| `<实际范围>` | `<源码/配置/生成器>` | `<已有或拟建页面/章节>` | `<configured/declared/inferred + 证据与置信度>` | `<项目命令或人工检查；未运行则说明>` |

`configured` 表示项目配置映射，`declared` 表示 AGENTS、索引或 owner 文档的显式声明，`inferred` 表示从实现和引用关系推断。前两类仍需核实是否过期；来源冲突时报告冲突，不因存在配置就覆盖项目有效规则。新建候选页面不会自动把推断变成既有项目约定。

## 完成边界

- 入口可导航到已创建的内容，当前事实与设计目标分开；关键行为能追溯到证据。
- 核实引用路径和项目命令，在环境与授权允许时执行相关验证；生成物按事实源和生成器更新，不手工补齐未知产物。
- 报告实际覆盖范围、未建立的候选 owner、待确认语义和未运行检查，不把初始地图描述成已穷尽整个仓库。
