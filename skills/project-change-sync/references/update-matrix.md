# 更新矩阵

下列路径仅表示职责；映射到项目实际 owner，不要求创建这些目录。双语、类型等价、预算等检查只在项目已有且变化相关时适用。

| 变化 | 首选所有者 | 需要检查的派生物和证据 |
|---|---|---|
| 系统组合、主循环、扩展点或高层运行路径 | `architecture.md` | 调用路径、架构图、集成测试 |
| 类型、语义、实现边界或生成 API | 对应 `subsystems/<name>.md` | 源类型、JSDoc、type-equiv、生成 freshness、测试 |
| 包配置、公开接口、限制、扩展点或消费者行为 | 包 README | manifest、exports、调用方、包测试 |
| 本地审查规则、资源/错误/安全模式 | `standards/` 或项目等价规则层 | 采纳依据、适用范围、验证方式、门禁覆盖、负例和审查证据 |
| 持久化设计理由、替代方案或架构取舍 | 项目 ADR/决策记录 | 决策、后果、当前路径、验证；交付状态按项目生命周期同步 |
| 真实事故和因果链 | `postmortem/` 或项目明确的 lessons 层 | 复现、影响、根因、预防和回归测试 |
| 机器契约源 | contract source + contract index | 生成器、漂移检查、兼容性和语义 owner |
| 生成参考或 catalog | canonical source/generator | freshness、生成命令、禁止手改 |
| 双语文档 | canonical pair + pairing metadata | 行结构、术语、链接和配对门禁 |
| 用户操作流程 | `guides/` / cookbook | 实际运行、失败恢复和结果验证 |
| 外部破坏性变化 | upgrade guide | 版本来源、旧/新行为、迁移和兼容性 |
| 没有可观察或契约变化的纯内部重构 | 通常无产品文档变化 | API/consumer 对比、相关 gate、测试和未验证项 |

`Lessons` 不是所有项目的默认类别；只有项目明确建立该层时才使用，否则按事故、Agent Note 或规范所有权映射。

## 规范与缺陷经验检查

仅在变更涉及规范、真实事故或可复用缺陷时检查；普通修复不因此要求新增规范或复盘文件。

1. **分开采纳与验证**：从有效 AGENTS、正式规范或项目决定核实规则是否已采纳；另查脚本、测试、人工判据、覆盖范围及实际结果。`observed` 是观察，`test-backed`、`mechanical` 和 `review-only` 是验证依据或方式，不是采纳阶段。只有确认门禁在所述范围启用且阻止违规通过时才称 `enforced`。
2. **核实经验来源**：确认现象、根因、修复和更早检测办法有证据。已有规则覆盖时检查规则或验证的缺口，不重复发明一条规范；局部缺陷可由 PR 与回归测试承载。
3. **检查提升条件**：候选应有稳定的预防规则、明确范围与例外，以及能检测失败模式的测试或门禁。缺少检测证据时列为待补；无法自动化时须有可操作的人工判据，并由项目明确接受其 `review-only` 局限。
4. **核实项目决定**：技术条件满足只支持提出候选，正式采纳需要项目决定或明确授权。复发次数等阈值仅采用项目政策；候选不写成当前要求，历史事故不重写成规范。已采纳规则与来源记录应能相互追溯。

在报告中分别写明经验或候选、采纳依据、验证覆盖与未满足条件。没有新建规范或 postmortem 不自动构成 `missing`：要求新增记录须有已确认适用的项目规则或任务要求；已有 owner 内容过时仍按同步状态判断。新的改进建议单列，影响结论的实质疑问用 `review-required`。本 Skill 保持只读，不修改规则、门禁或经验记录。
