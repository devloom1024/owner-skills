# 项目文案规范

这是编辑判断 Skill，不是机械删字脚本。默认只读审查；用户明确要求修改时才编辑，并保留所有改变行为的命题。

## 输入和范围

1. 从请求和上下文确定范围：指定文件就处理文件，指定 PR/diff 就核实对应基准，“全仓库润色”已明确授权仓库范围。无需再索要形式化 `scope` 或模式参数；只有无法合理确定且影响结果时才提问。
2. 遵守项目 AGENTS 排除 vendor、归档快照、生成产物和不在授权范围内的路径。
3. 先读取文档/代码所有者，再判断句子；文档归属按项目规则，涉及重组时可参考 `project-docs`，不要求安装它。
4. 审查请求默认只读；改写请求默认在范围内直接编辑并报告。只有用户要求逐项确认时使用 `interactive`；遇到会改变契约的实质歧义先保留原意并说明，不把整项任务停在规划。

## 保留完整命题

编辑前识别 actor、action、condition、timing、ordering、modality、negative guarantee、exception、ownership、side effect、failure 和 consequence。保留契约、限制、时序、失败、所有权和验证；只删除装饰、重复、实现过程、审查对话和推理串。

## 按内容位置检查

- 公共 JSDoc：返回区别、异常、 side effect、所有权、时序、取消和持久性；
- 内部注释：不显然的结构、不变量、竞态、权限和失败行为；
- README：消费者配置、语义、失败、限制、扩展点和可见影响；
- Agent Note：理由、替代方案、后果、验证和覆盖缺口；
- 测试注释：只说明不显然的夹具、真实入口、间接观察和平台适配；
- 指南：前置条件、真实入口、可观察成功和失败恢复；
- 诊断/UI 文案：主体、违规规则、影响和下一步；
- proposed/implemented：明确未来目标与已交付事实的时态边界。

## 工作流和输出

1. 阅读 owners、当前事实和相关设计；
2. 搜索重复规则、过期状态、推理泄漏和缺失命题；
3. 按 `keep`、`add`、`trim`、`restore`、`restructure`、`defer` 分类；
4. 更新 owner 后再更新派生文档或翻译；
5. 编辑后运行项目已有且与本次修改相关的链接、文档、locale、snapshot 或行为检查，以及 `git diff --check`；只读审查不运行会改写产物的命令；
6. 报告清晰修改、保留内容、延后项、来源和已运行命令。
