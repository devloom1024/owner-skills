# Exceptions & Versioning — 规范例外和版本治理

## Exceptions / 例外不是坏事，未记录的例外才会导致失控

对 `SHOULD` 基线可因项目品牌、内容、平台、输入方式或业务证据作适配；例如密集编辑器、复杂看板和长表格。先遵循项目既有设计系统与审批方式，不要求为已有规则重复补例外单。适用优先级见 [规范强度](normative-levels.md)；记录理由不等于可以取消安全、必要语义或无障碍约束。

## Exceptions / 例外记录模板

| 字段 | 必填说明 |
|---|---|
| ID / 提出日期 | 可追踪 |
| 所属页面/模式 | 具体路径和 Pattern |
| 偏离内容 | Token、导航方式、交互规则 |
| 原因与候选方案 | 为什么现有规范不适合 |
| 用户影响和风险 | 可访问性/学习成本/跨端差异 |
| 负责人/审批 | 项目可自行设责任人 |
| 到期/复审条件 | 什么时候合并进规范或移除 |

## 版本说明

- `MAJOR`：改变共享设计语言或 Pattern 基础行为，可能要求多个项目同步调整。
- `MINOR`：新增 Pattern、平台规则或向后兼容的 Token 语义。
- `PATCH`：错别字、链接、阐释、不会改变实现结果的规则澄清。

版本由 owner-skills 仓库统一管理；维护时按受影响范围同步规范、Token 引用、示例和路由，并写未发布记录，不自动创建 tag。项目记录实际采用的仓库 tag/commit 和本地适配，不维护一个与安装内容脱节的独立规范版本号。
