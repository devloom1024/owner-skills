# Normative Levels — 规范强度

本规范使用三种强度，避免把推荐基线误读为平台硬性要求：

| 强度 | 文档用词 | 含义 |
|---|---|---|
| `MUST` | 必须、不得、禁止 | 安全、无障碍、必要语义行为和平台强制约束；项目例外不能将其降为可选。约束冲突时保留保护目标并说明适配依据。 |
| `SHOULD` | 默认、建议、推荐、优先 | 设计系统基线；可以因内容、平台、输入方式或业务证据调整，并说明原因。 |
| `MAY` | 可选、可以、适用时 | 仅在任务需要时采用，不构成跨页面或跨平台承诺。 |

## 规范优先级

1. 适用的安全、无障碍、必要语义行为和平台强制约束；
2. 项目已采用的设计系统、组件、Token 和批准的适配；
3. 本 Skill 的默认视觉、布局和 Pattern 建议；
4. 示例及示意代码。

在本 Skill 的默认层内部，先读基础规则和组件语义，再读 Pattern 共享行为及平台呈现。项目无需把既有设计系统逐项登记为例外；只对新产生的偏离按项目流程记录。例外可以覆盖 `SHOULD` 基线，不能使关键操作不可达或牺牲必要的安全与无障碍。

## 默认解释

- 没有明确强度标记的尺寸、断点、密度和视觉数值，按 `SHOULD` 处理。
- 键盘可达、焦点管理、错误恢复、数据不丢失、危险操作后果、触摸/辅助技术的关键入口，按 `MUST` 处理。
- `桌面端` / `移动端` 文件描述的是推荐载体，不是设备身份判定；实际决策仍由容器空间、输入方式和运行平台共同决定。
- 例外记录至少包含偏离内容、原因、用户影响、负责人和复审条件，模板见 [例外 & Versioning](exceptions-versioning.md)。

## 维护要求

新增规则时，在句子或小节标题中标注 `MUST`、`SHOULD` 或 `MAY`；新增数值必须进入 [Design Token](../02-foundations/design-tokens.md) 或说明为何不属于全局 Token。
